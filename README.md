# TREMOR_SCLAD
Сайт для складского учета. Проект для организации "TREMOR HANDLESS". Все права защищены, сайт не является публичным.

## Локальная проверка проекта

Frontend: из папки `frontend` выполните `npm ci`, `npm test`, `npm run lint`, `npm run build`. Все проверки выполняются локально; GitHub Actions для них не нужны.

Backend читает `DATABASE_URL` из локальной `backend/.env` либо переменных окружения. Образец — `backend/.env.example`; значения ключей Ozon и строка подключения не должны попадать в Git. Наличие ключей пока не включает внешний FBS-клиент.

В `backend/go.mod` закреплена минимальная версия Go 1.26.9. При `GOTOOLCHAIN=auto` Go выбирает и при необходимости загружает подходящий toolchain; при отключённом автовыборе потребуется установленная версия не ниже указанной.

## Проверка backend и приёмки

Из папки `backend` запустите интеграционные тесты в PowerShell:

```powershell
$env:TEST_DATABASE_URL = 'postgres://USER:PASSWORD@127.0.0.1:5432/TEST_DB?sslmode=disable'
go test ./... -count=1 -v
Remove-Item Env:TEST_DATABASE_URL
```

Используйте отдельную тестовую базу PostgreSQL. Пользователь должен иметь право создавать схемы. Интеграционные тесты создают собственные схемы, применяют необходимые миграции и удаляют только свои схемы после проверки. Для приёмки используются 001 и 003–009, для стеллажей — 010, для сборки и проблем — 011–018. Сквозная проверка использует полноценную схему склада и обработчики приёмки. Миграция 002 с начальными данными для тестов не нужна. Без `TEST_DATABASE_URL` интеграционные тесты пропускаются; обычный `go test ./...` не подтверждает поведение базы.

Дополнительно из `backend`: `go vet ./...`, `gofmt -l cmd internal`, `go mod tidy -diff`. Последние две команды не должны показывать расхождений. Для файлов Go и контрольных сумм закреплены окончания строк LF в `.gitattributes`.

Проверяются сохранение группы товаров и размещений, отмена и повторная отмена, недостаточный остаток для отмены, завершение с неразмещёнными товарами или устаревшим списком размещений, защита завершённой приёмки, два одновременных размещения, безопасное удаление истории, страницы по 5 записей и сортировка по времени в обоих направлениях, включая одинаковые даты и удалённый курсор.

Ручная проверка исправления истории:

1. Завершите приёмку с размещённым товаром.
2. Начните следующую приёмку и разместите в ней товар, оставив её активной.
3. Обновите страницу: активная приёмка должна восстановиться, а завершённые — остаться в отдельном блоке «История приёмок» без ошибки загрузки.
4. Нажмите глаз в строке завершённой приёмки: внутри строки откроются связанные товары с артикулами, ячейки и количества. Повторное нажатие плавно сворачивает содержимое. Номер приёмки — обычный текст. Просмотр истории не меняет активную приёмку.

История загружается по 5 приёмок. Стрелка возле «Завершена» переключает порядок по времени завершения: от новых к старым или наоборот; выбранный порядок запоминается в браузере. При одинаковом времени номер используется только как стабильный дополнительный ключ. Кнопки «Предыдущая» и «Следующая» переключают страницы, круглая стрелка обновления возвращает к первой странице выбранного порядка. Список остаётся видимым во время загрузки, фон страницы не меняется при раскрытии строк. После завершения текущей приёмки список обновляется автоматически. Активные и скрытые сессии не входят в историю, отменённые размещения не входят в её итоги.

Галочка возле обновления открывает подтверждение завершения истории за день. Экспорт в Excel и подготовка истории к следующему дню пока не реализованы: подтверждение не меняет и не удаляет записи.

Удаление завершённой приёмки из истории требует подтверждения. Оно скрывает запись из списка и загрузки последней приёмки, не меняя остатки, размещения и активную сессию. Повторный запрос удаления безопасен. Для этого применяется отдельная миграция `007_receiving_history_deletion.sql`. Исходные записи остаются в базе с отметкой `deleted_at`; вернуть запись можно через базу, отдельной кнопки восстановления пока нет.

Чтобы применить миграцию удаления с теми же настройками подключения, что у API, запустите из `backend`: `go run ./cmd/migrate-receiving-history`.

## Сборка и проблемные заказы

Заказы, проблемы, отборы, резервы, история и разбор сохраняются сервером. Правила — в [problem-resolution-rules.md](docs/assembly/problem-resolution-rules.md), итоговая матрица проверок и ограничения — в [final-chain-validation.md](docs/assembly/final-chain-validation.md). Внешний клиент Ozon ожидает официальный контракт; живые FBS-вызовы сейчас отключены.

Для существующей базы с подготовленными таблицами склада команда `go run ./cmd/migrate-assembly-preview` из `backend` применяет отсутствующие миграции 011–018. Это отдельная операция обновления БД, а не часть запуска тестов или обычной очистки кода.
