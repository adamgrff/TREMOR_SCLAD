# Статистика Главной

`GET /api/home/statistics?period=today` — только чтение, один согласованный
снимок PostgreSQL (`REPEATABLE READ READ ONLY`), `Cache-Control: no-store`.
Без period или с пустым period используется today. Неизвестный период либо
повторение period возвращает HTTP 400. Ошибка БД — HTTP 500, без ложных нулей.

## Период

Часовой пояс сайта — Asia/Krasnoyarsk (UTC+07:00).
today начинается сегодня в 00:00; 7d — в 00:00 шесть дней назад;
30d — в 00:00 двадцать девять дней назад. Верхняя граница — момент запроса,
не включительно. Это календарные периоды, включающие текущий день.

## Доступные показатели

- receiving.sessions: завершённые сессии по completed_at внутри периода.
  Скрытая история (deleted_at) не отменяет факта проведённой приёмки.
- receiving.receivedQuantity: сумма receiving_intake_events.quantity по
  occurred_at за период. Всегда число; при отсутствии событий — 0.
- receiving.placedQuantity: сумма receiving_placement_items.quantity для
  действующих размещений по receiving_placements.created_at за период.
  Отменённые размещения исключаются; размещение незавершённой сессии учитывается.
- receiving.pendingQuantity: текущее количество receiving_session_items
  всех сессий status=active, независимо от периода.
- stock.totalQuantity: весь cell_stock, включая архивные товары.
- stock.occupiedCells: число уникальных ячеек с положительным остатком.
- stock.totalCells: все существующие ячейки.
- stock.skuCount: число SKU с положительным суммарным остатком, включая архивные.
- stock.lowStockCount / lowStockItems: SKU с суммарным остатком 1–5 включительно,
  включая архивные. Ноль исключён. Сортировка: quantity, затем sku.
- assembly.queuedOrders: ozon-заказы status=queued с импортированной текущей
  версией в assembly_order_heads, как в GET /api/assembly/orders.
- assembly.activeOrders: ozon-заказы status=in_progress.
- assembly.completedOrders: число уникальных реальных заказов со статусом
  completed и событием completed в выбранном периоде.
- assembly.averageAssemblySeconds: среднее completed.occurred_at - started.occurred_at
  в секундах для корректных пар одного order_id/cycle_id, завершённых в периоде.
  Старт может находиться до начала периода. Пары с отрицательной длительностью
  и завершения без доказанного старта в среднее не входят.
- assembly.problemOrders: число разных ozon-заказов, для которых создана
  проблема в периоде (assembly_problem_records.created_at). Несколько проблем
  одного заказа считаются один раз. Разрешённые/возвращённые также учитываются:
  это история возникновения проблем, а не текущее число открытых проблем.

Все поля stock, pendingQuantity, queuedOrders и activeOrders не зависят от периода.
Исторические preview-заказы исключены из статистики реальной сборки.

Все числовые показатели возвращают число, не null. При отсутствии завершений
completedOrders=0; при отсутствии корректных пар averageAssemblySeconds=0.
История последних действий в этот endpoint не входит.

## Журнал жизненного цикла сборки

Миграция `021_assembly_lifecycle_events.sql` добавляет assembly_lifecycle_events:
order_id, cycle_id, event_type (started/completed), occurred_at, request_id и
operation_id. Допускаются только реальные ozon-заказы. UPDATE, DELETE и TRUNCATE
запрещены; один тип события на цикл и одна запись на подтверждённый запрос/
операцию обеспечены уникальными ограничениями.

started записывается в applyWarehouseAssemblyOperation после успешных проверок
start и резервирования, в одной транзакции с состоянием и request receipt.
cycle_id равен requestId старта. Повтор подтверждённого запроса возвращает
сохранённый ответ и не выполняет операцию повторно. Новый допустимый start
после возврата в очередь начинает новый цикл, не переписывая прежний.

В текущем процессе finish без проверенного результата Ozon не завершает заказ.
completed записывается в finalizeOzonConfirmation только при фактическом
успешном завершении исходного finish, после проверки applied, отборов, коробки,
резервов и отсутствия блокирующих проблем. Клик finish, неизвестный/отклонённый
результат, незавершённые, проблемные и отменённые заказы не создают успешного
завершения. Официальный внешний клиент по-прежнему не подключается этой задачей.

При регистрации confirm_shipment в неизменяемом payload сохраняется
lifecycleCycleId. Поэтому позднее подтверждение связывается с циклом исходного
finish, а не с последним стартом на момент получения подтверждения. Время
completed — серверное время фиксации успешного завершения, не время скана и
не присланный извне observedAt. Длительность включает ожидания внутри цикла,
в том числе ожидание подтверждённого завершения Ozon.

Старые операции и timestamps не восстанавливаются. Уже завершённый до журнала
заказ без события не попадает в счётчик. Если старый активный заказ успешно
завершится после внедрения журнала, записывается новое доказанное completed,
но started не придумывается: такой заказ учитывается в completedOrders,
не участвует в averageAssemblySeconds.

Миграция подготовлена в `go run ./cmd/migrate-assembly-preview` из backend.
Новая версия API требует миграцию 021 до обработки start/finish и статистики.

## Журнал принятого количества

Миграция `020_receiving_intake_events.sql` добавляет неизменяемый журнал:
session_id, product_id, положительное quantity и occurred_at (clock_timestamp()).
UPDATE, DELETE и TRUNCATE запрещены триггерами; ссылки на сессию и товар — RESTRICT.
Строки журнала не зависят от текущего содержимого receiving_session_items.

Единственная точка записи — addReceivingSessionQuantity. Существующие добавления
по SKU, по ID и создание товара с начальным количеством вызывают эту операцию
после блокировки активной сессии. Изменение остатка и событие фиксируются одной
транзакцией. Проверка существующего requestId выполняется до вызова операции:
повтор подтверждённого запроса не создаёт дополнительного события.

PUT-корректировка текущего количества, удаление ожидающего SKU, размещение и
отмена размещения не добавляют и не меняют события поступления. Журнал отражает
добавления, а не текущее количество или его последующие исправления.

Миграция не восстанавливает старые поступления из остатков и размещений и
не меняет их. Поэтому receivedQuantity отражает только события, записанные
после внедрения журнала, а не полную ретроспективу старых операций.
Запуск миграции подготовлен в существующей команде из backend:
`go run ./cmd/migrate-product-catalog`. Перед запуском новой версии API нужна
миграция 020; без таблицы endpoint вернёт ошибку, а не ложную статистику.
