# Хранение проблем: этап 2

Бизнес-правила: [problem-resolution-rules.md](problem-resolution-rules.md). Этот этап меняет хранение и защиту сохранённых данных. Проверки реальных остатков, резервирование, операции Ozon и физический разбор подключаются на следующих утверждённых этапах.

## Модель

- `assembly_order_records` — постоянный ID заказа и состояние; номер уникален в пределах источника.
- `assembly_order_versions`, `assembly_order_positions` — неизменяемые версии состава заказа и позиции с самостоятельными ID.
- `assembly_problem_records` — несколько независимых проблем одного заказа. Каждая получает UUID, исходную версию заказа и исходные данные причины/комментария, текущую версию и состояние решения. `resolution_status` отделён от `disposition`: решение проблемы ещё не означает возврат.
- `assembly_problem_affected_positions` — неизменяемый исходный список затронутых позиций. `assembly_problem_positions` — текущие сведения о нехватке; они могут меняться после проверки, не уничтожая исходные данные.
- `assembly_pick_records`, `assembly_cell_references` — отдельные записи отборов и ссылки на ячейки. `assembly_problem_pick_links` хранит неизменяемый снимок отборов на момент проблемы; `assembly_workspace_pick_links` — текущие отборы активной сборки.
- `assembly_problem_events` — отдельные события с UUID, порядком, типом, временем события и серверным временем записи. События дописываются; UPDATE/DELETE запрещены триггером. UI-группировка повторов не удаляет события.
- `assembly_preview_drafts` — версия рабочего состояния и ссылки на записи; составы заказов, проблемы и отборы восстанавливаются из отдельных таблиц.

Дополнительные JSON-поля сохраняют совместимость существующего интерфейса. Они содержат отображаемые параметры и комментарии, но не заменяют отдельные связи заказа, позиции, проблемы, отбора и события.

## Совместимость и ограничения этапа

GET/PUT `/api/assembly-preview/draft` остаются адаптером существующего интерфейса. Запись нормализованных данных, версии рабочего состояния и результата идемпотентного запроса проходит в одной транзакции с блокировкой рабочего состояния. Повтор requestId с тем же содержимым возвращает сохранённый результат; устаревшая версия получает 409.

Дополнительно доступны GET `/api/assembly/problems` (не возвращённые проблемы), `?includeClosed=true`, `?order=НОМЕР` и GET `/api/assembly/problems/{UUID}`. Просмотр архива в интерфейсе остаётся этапом 9.

Backend отклоняет удаление сохранённой проблемы, переписывание истории, исходных отборов и контекста сборки. Для возврата должны быть решены все проблемы заказа; отмена и обязательный разбор блокируют возврат. Интерфейс проверяет тот же набор проблем, а не только выбранную строку. Повторная проблема создаётся отдельной записью, старая сохраняется.

Временный адаптер ещё принимает результат решения от frontend. Серверные проверки остатков, пригодности, резерва и доказательств решения относятся к этапу 4; наличие `resolved` сейчас не является доказательством реальной складской проверки. Автоматические исходы Ozon и отмены здесь не реализованы.

Существующие отборы обозначены `source=preview_snapshot`: они не создают складских движений. Их идентичность определяется заказом, порядковым номером и содержимым снимка. `warehouse_operation_id`, `warehouse_product_id` и `warehouse_cell_id` подготовлены для этапа 5. Временные ячейки имеют область `preview`; их код нельзя считать уникальным ID реальной ячейки. Настоящие операции должны получить собственные ID и связи с реальными ячейками, а не использовать ключ снимка.

Старые отборы не содержат времени скана: `occurred_at` для них остаётся NULL. Серверное время записи не выдаётся за время скана. У старой проблемы без истории создаётся событие создания с известным временем самой проблемы. Оператор не записывается, пока приложение не предоставляет подтверждённую личность пользователя. Полный контекст новых действий дополняется с этапа 3.

## Миграция и откат

Из каталога `backend` выполнить `go run ./cmd/migrate-assembly-preview`. Команда применяет отсутствующие миграции 011 и 012. Миграция 012 целиком транзакционная: переносит сохранённые данные, сохраняя версию рабочего состояния, и оставляет исходную копию в `assembly_workspace_migration_backup`. Товары, складские остатки и резервы не изменяются.

Во время обновления остановить старый API, выполнить миграцию и запустить новый API: старый бинарник не понимает ссылки нормализованного состояния. Перед обновлением сохранить дамп и прежний бинарник. Контрольная Git-точка: `checkpoint-before-problem-storage-2026-10-11`.

Если после обновления были новые действия, откат нельзя выполнять из начальной копии: это потеряет новые изменения. Сначала остановить запись, выгрузить актуальное состояние через `assembly_load_workspace(state)` и сохранить полный дамп. Для возврата старого API рабочее состояние преобразовать в прежний JSON, сохранив текущую версию; нормализованные таблицы и историю не удалять. Начальная копия пригодна только для отката без действий после миграции. Возврат к новой версии после такого отката требует отдельного согласованного переноса, а не простого пропуска миграции по наличию таблиц.

## Проверки

Интеграционные тесты PostgreSQL используют отдельные временные схемы и проверяют перенос старого состояния, несколько проблем одного заказа, неизменность контекста/истории, атомарный отказ возврата, повторные запросы, конфликт двух записей, повторное возникновение проблемы и сохранность складского количества. Дополнительно выполняются Go test/vet, frontend lint/build и существующие проверки остатков/истории.
