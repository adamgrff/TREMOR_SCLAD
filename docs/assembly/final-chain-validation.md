# Этап 10: комплексная локальная проверка

Дата: 14.10.2026. Исходный коммит: `28c4575`. Точка отката: `checkpoint-before-assembly-final-checks-2026-10-14`.

## Итог

Проверена реализованная цепочка: импорт заказа в общую модель БД → создание проблем → сопоставление товара → серверная проверка остатков → явный возврат → резерв → отбор → повторная проблема → продолжение → подтверждение коробки → журнал Ozon → завершение либо подтверждённая отмена → передача в разбор → физический возврат → архив.

Тесты выполнялись локально с настоящим PostgreSQL и складскими транзакциями. Заказы и ответы адаптера — контролируемые тестовые данные в отдельных схемах, не живые FBS-заказы. HTTP-сценарии вызывают production handlers через реальные TCP-соединения; они не подменяют серверные проверки frontend-вычислениями. Одна проверка использует полноценные миграции склада и реальные обработчики «Приёмки», остальные — изолированные профильные схемы.

## Матрица сценариев

| Сценарий | Проверка и результат |
| --- | --- |
| Несколько причин одного заказа | Mapping устраняет неизвестный SKU, но создаёт отдельную нехватку. Нерешённая причина запрещает возврат; положительное число остатков не закрывает другую причину. |
| Изменение остатков | Успешная проверка не даёт бессрочного разрешения. Уменьшение остатков до возврата отклоняет действие и сохраняет актуальную нехватку. |
| Связь с «Приёмкой» | Размещение товара устраняет нехватку, отмена размещения вновь блокирует возврат. Повторное размещение и завершение приёмки позволяют продолжить. |
| Частичный отбор | Сохраняются SKU позиции заказа, ID складского товара и ячейки, ID операции и время. При продолжении остаётся один исходный отбор и резерв только оставшихся единиц. Старое подтверждение ячейки сбрасывается. |
| Повторная проблема | После возврата дважды создаётся новая причина с новым problemId и сохранённым частичным прогрессом. Старые закрытые причины и их события не изменяются. |
| Два клиента / вкладки | Конкурирующие HTTP-команды с одной версией: одна проходит, другая получает 409. Hook проверен в двух независимых экземплярах, включая загрузку состояния после конфликта. |
| Повторные нажатия | Во время запроса hook не отправляет второй intent. Повтор того же requestId возвращает прежний результат без новых отборов, событий или зачислений. |
| Обрыв до запроса | Не выполненная команда повторяется с тем же UUID. Другие действия не подменяют неопределённую команду. |
| Потеря ответа после commit | HTTP-сервер выполняет команду, затем закрывает соединение без ответа. Повтор создания проблемы, mapping, возврата, отбора, отмены отбора, передачи, физического возврата и завершения не дублирует действие. |
| Ошибка записи БД | Искусственная ошибка при зачислении разбора возвращает 500. Остатки, pending-товар, история и журнал возвратов сохраняют состояние до попытки. Повтор после устранения ошибки проходит один раз. Сообщение `cycle return failure` в тестовом логе ожидаемо. |
| Перезагрузка и повторное подключение | После каждой HTTP-команды GET восстанавливает её состояние, включая этапы сканирования и pending-товар разбора. Новый сервер с новым пулом PostgreSQL восстанавливает тот же снимок; устаревшая версия отклоняется. |
| Отмена частично собранного заказа | Проверенный тестовый receipt освобождает только оставшийся резерв. Отобранная единица не появляется в остатках при отмене, передаче, запуске разбора или скане товара. Зачисление происходит после исходной ячейки. |
| Завершение Ozon | Без проверенного результата завершения нет. Повтор исходного receipt не завершает дважды. Внешний повтор не создаёт вторую бизнес-операцию. |
| История и архив | События добавляются, их старый префикс неизменен. Закрытые причины доступны отдельно; рабочий список исключает их. Повторы запросов не добавляют повторных событий. |

## Найденный и исправленный дефект

**Устаревший экран после безопасного повтора.** Вкладка A списывала единицу, теряла ответ, вкладка B выполняла следующий отбор. A повторяла исходный UUID и получала корректный сохранённый receipt, но показывала его старый снимок без отбора B. Серверные остатки были правильными, однако интерфейс отображал устаревшие прогресс и версию.

`useAssemblyDraft` теперь отмечает неопределённый запрос и после успешного повтора получает актуальное состояние отдельным GET. До успешного восстановления новые складские команды заблокированы. Если GET тоже прервался, сохраняется исходный запрос с тем же UUID, а не создаётся новый. Бизнес-правила, серверная идемпотентность, резервирование и архитектура этапов 1–4 не менялись.

Регрессионный тест сначала воспроизвёл дефект (ожидалось два отбора, показывался один), затем прошёл после исправления. Других дефектов в выполненных сценариях не обнаружено; это не утверждение об отсутствии всех возможных ошибок.

## Оставшиеся ограничения

1. Официальный контракт Ozon пока не подключён. Реальные FBS-заказы, ответы, отмены и подтверждения в Ozon не проверены; использованы проверяемые тестовые receipt адаптера. Потерю реального внешнего ответа необходимо проверить отдельно после подключения официального клиента. Неопределённый исход не считается успешным и не повторяет бизнес-операцию автоматически.
2. Для `missing_in_cell`, `damaged_product` и `other` backend требует доказательства соответствующей обработки. Полноценных операторских экранов физической проверки, корректировки расхождений, карантина/утилизации и подтверждения устранения другой причины пока нет. Положительный остаток или комментарий не обходят эти требования. В отдельных профильных тестах доверенное evidence создаётся как тестовая предпосылка, а не через отсутствующий пользовательский процесс.
3. Разбор возвращает исходные единицы полного заказа в исходные ячейки. Частичная переработка изменённого состава и обработка повреждённых единиц остаются отдельными согласуемыми процессами. Повреждённый товар не зачисляется как пригодный.
4. Точное время старых сканов без сохранённого timestamp неизвестно. Новые операции сохраняют серверное время.
5. Авторизация и привязка событий к конкретному оператору приложением пока не реализованы. Физический сканер и действия человека на складе не проверялись; тестировались коды и серверные операции.
6. Go race detector не запускался: локальный Go имеет `CGO_ENABLED=0`, C-компилятор отсутствует. Конкуренция проверена настоящими параллельными HTTP/SQL-командами; это не заменяет race detector.
