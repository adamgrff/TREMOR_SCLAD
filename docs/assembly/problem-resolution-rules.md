# Проблемные заказы: правила решения — этап 1

## Границы документа

Документ фиксирует правила для дальнейших этапов, а не описывает уже реализованный backend. На этапе 1 не меняются UI, API, таблицы, складские остатки и интеграция Ozon.

Источники: утверждённый пользователем десятиэтапный план и уточнения; пакет `TREMOR-assembly-codex-handoff`, документы 03, 04 и 06. Новые указания пользователя имеют приоритет над пакетом. В частности, подтверждённая ячейка позволяет сканировать нужные товары в любом порядке; прежнее описание обязательной пары сканов для каждой единицы не применяется.

## Согласованная модель резерва

- Резерв создаётся при начале сборки, включая первый запуск заказа после проблемы, обнаруженной до сборки. Простое создание проблемы из очереди резерв не создаёт.
- Резерв скрыт от интерфейса. Оператор не создаёт и не освобождает его вручную.
- Подтверждённые отборы учитываются отдельно: товар уже списан из ячейки, закреплён за заказом и не входит в остаток ячейки или оставшийся резерв.
- Требуется добрать = количество заказа − действующие подтверждённые отборы. Отменённые и возвращённые отборы не считаются собранными.

Правила жизненного цикла для реализации: при обычной остановке в проблемные оставшийся резерв сохраняется. При продолжении используется существующий резерв, а не создаётся второй. При подтверждённой отмене освобождается только резерв неотобранного товара; отобранный товар остаётся закреплён до физического возврата. После завершения или полного разбора оставшегося резерва нет. Изменение состава заказа требует пересчёта его резерва в той же операции.

Для проверки позиции: доступно этому заказу = фактический пригодный остаток − резервы других заказов. Это равно свободному остатку плюс собственному оставшемуся резерву. Собственный резерв не прибавляется к фактическому остатку второй раз; уже отобранные единицы не прибавляются к остатку склада. Доступное количество должно покрывать количество, которое осталось добрать.

При расхождении или повреждении неподтверждённый физический остаток не считается пригодным источником отбора. Корректировка реального остатка выполняется отдельной учитываемой складской операцией, а не редактированием числа в проблеме.

## Общие критерии решения и переходов

1. Проблема относится к конкретной причине и затронутым позициям. У заказа может быть несколько нерешённых проблем одновременно.
2. Решение одной проблемы не решает другие и не разрешает возврат автоматически. Проверка может выявить дополнительную проблему; она добавляется отдельно, исходная причина не подменяется.
3. Оператор может подтвердить физическую проверку, но не обойти серверные проверки кнопкой «Решена».
4. Возврат требует явного действия оператора. Backend повторно проверяет все проблемы, состояние Ozon, пригодность товара, остатки, резерв и отсутствие незавершённых обязательных возвратов. Нет параллельной активной сборки этого заказа.
5. Для продолжения восстанавливаются действующие отборы. Ожидание следующего скана рассчитывается заново; старое подтверждение ячейки после устранения проблемы не используется как разрешение списать товар.
6. Проблема имеет состояние «Ожидает решения» или «Решена». «Возвращена в сборку» — результат дальнейшего перехода заказа, не универсальный исход любой решённой проблемы. Для отмены, подтверждения Ozon и разбора существуют другие исходы.
7. При повторном возникновении причины создаётся новая проблема, связанная с предыдущей. История старой проблемы не очищается.

## Правила по типам

### Недостаточно товара

**Действие:** оператор пополняет склад через «Приёмку» и нажимает «Обновить остатки».

**Решена:** backend проверил актуальные пригодные остатки с учётом чужих резервов; для всех затронутых позиций хватает товара, чтобы добрать заказ. Наличие товара у другого заказа не даёт разрешение на отбор.

**Далее:** заказ остаётся в проблемных с доступным возвратом только при отсутствии остальных препятствий. По явному «Вернуть в сборку» выполняется повторная проверка и начинается либо продолжается сборка. Если остатки изменились, возврат отклоняется и фиксируется актуальная нехватка.

### Товар отсутствует в ячейке

**Действие:** оператор проверяет конкретные товар и ячейку. Если товар найден, подтверждает физическую проверку. Если найден в другой ячейке, подтверждает корректное размещение через складскую операцию. Если товар не найден, оформляет расхождение фактического остатка; при нехватке пополняет склад.

**Решена:** сохранены результат физической проверки, затронутая ячейка, товар и комментарий; ошибочные данные размещения исправлены; новый план использует подтверждённые пригодные источники. Одного положительного числа в БД недостаточно.

**Далее:** если после исправления возникла нехватка, создаётся отдельная проблема «Недостаточно товара». Возврат разрешён только после устранения всех причин; уже выполненные отборы сохраняются.

### Неизвестный товар / SKU

**Действие:** оператор выбирает складской товар и сохраняет постоянное сопоставление SKU Ozon с внутренним ID товара. Перед сохранением проверяется соответствие товара.

**Решена:** сопоставлены все затронутые неизвестные SKU; состав и количества заказа повторно проверены. Простое создание нового товара не считается сопоставлением.

**Далее:** проверяются остатки и остальные причины. Если обнаружена нехватка, создаётся новая проблема этого типа. Сопоставление не запускает сборку автоматически; возврат — отдельное действие после общих проверок.

### Повреждённый товар

**Действие:** оператор фиксирует товар, количество, ячейку или исходный отбор и комментарий; отделяет повреждённые единицы и оформляет их исключение из пригодного остатка через учитываемую складскую операцию.

Если повреждён уже отобранный товар, он не считается готовой позицией заказа. Его исходное движение и корректировка прогресса сохраняются. Требуется подтверждённая обработка конкретных единиц; их нельзя автоматически вернуть в пригодный остаток. При необходимости физического возврата они передаются в разбор с дальнейшим учётом повреждения. Это не равнозначно отмене заказа целиком.

**Решена:** повреждённые единицы исключены из доступных источников и готового количества заказа; обязательные операции по ним завершены и сохранены. Для замены используются только пригодные единицы.

**Далее:** при нехватке замены создаётся отдельная проблема недостаточного остатка. Заказ можно продолжить после устранения всех проблем и завершения обязательной обработки повреждённых отборов.

### Ошибка данных заказа

**Действие:** оператор сверяет состав и количества с актуальными данными Ozon и запускает повторное получение/проверку заказа. Комментарий или произвольная правка локальной копии не заменяют проверенный источник.

**Решена:** сервер получил и проверил корректную версию заказа; все SKU сопоставлены либо вынесены в отдельные проблемы; количества и действующие отборы согласованы с новым составом. Резерв пересчитан согласованно.

Если уже отобран товар, исключённый из состава, или собрано больше нового требуемого количества, лишние единицы не теряются: они отмечаются для физического разбора. Если Ozon подтвердил отмену, применяется правило отменённого заказа.

**Далее:** возврат в сборку после устранения всех препятствий. При изменении уже подтверждённой этикетки требуется новая проверка отправления; прежнее подтверждение не переносится автоматически.

### Другая проблема

**Действие:** оператор вводит обязательное описание причины. После её устранения подтверждает выполненные действия обязательным комментарием; при затронутых товарах указывает позиции.

**Решена:** сохранены описание и подтверждение устранения; серверные проверки не выявляют препятствий для выбранного дальнейшего действия. Ручное подтверждение не отменяет нехватку, неизвестный SKU, отмену, ошибку Ozon или необходимость разбора. Обнаруженная известная причина регистрируется отдельно.

**Далее:** обычный возврат после общих проверок. Отмена и разбор проходят через свои состояния; их нельзя заменить ручным закрытием «Другой проблемы».

### Отменённый заказ без отборов

**Действие:** оператор подтверждает закрытие отменённого заказа. Перед этим сервер сверяет актуальную отмену в Ozon и отсутствие действующих отборов/незавершённых движений.

**Решена/закрыта:** отмена подтверждена, оставшийся резерв освобождён, физических товаров за заказом нет.

**Далее:** статус заказа «Отменён», архив/история. Он не возвращается в очередь или сборку; кнопки разбора нет. Если до подтверждения обнаружены отборы, применяется следующий сценарий.

### Отменённый заказ с отборами

**Действие:** оператор нажимает «Передать в разбор». Сервер проверяет отмену и действующие отборы, фиксирует необходимость физического возврата и освобождает только резерв неотобранного товара.

**Решена/закрыта:** передача в разбор ещё не является решением. Необходимые физические возвраты завершены и связаны с исходными движениями; отсутствуют незавершённые движения и резервы. Повреждённый товар не зачисляется в пригодный остаток без соответствующей обработки.

**Далее:** при передаче — «Ожидает разбора», затем «Разбор», после завершения — «Разобран» и архив с сохранённой причиной отмены. Возврат в сборку запрещён.

### Ошибка Ozon и успешный повторный запрос

**Действие:** оператор повторяет именно неуспешную операцию. Сохраняются её назначение, ID заказа, ключ операции, время попыток и проверяемый результат. HTTP 200 без проверки содержимого не доказывает успех. При неизвестном результате сначала выясняется состояние операции, а не выполняется новое складское движение.

**Решена:** backend проверил фактический ответ/состояние Ozon для исходной операции. Повтор не создаёт повторных отборов, списаний или подтверждений.

**Далее зависит от назначения запроса:**

- Подтверждение полностью собранного и проверенного отправления: при подтверждённом успехе и отсутствии других препятствий заказ переходит в «Завершён» и историю. Повторная сборка не запускается.
- Получение/обновление данных заказа: данные обновляются; ошибка связи решена, но состав, SKU, остатки и другие проблемы проверяются заново. Заказ остаётся проблемным либо получает возможность явного возврата.
- Ozon сообщил отмену: создаётся проблема отмены; дальнейший путь зависит от наличия отборов.
- Ozon вернул отказ, ошибку или неопределённый результат: проблема остаётся нерешённой, ответ фиксируется в истории; локальные отборы автоматически не откатываются.

## Обязательный контекст и история

Историю начинаем сохранять на этапе 2. Фиксируются время backend, тип события, оператор (если поддерживается), заказ, проблема, позиции, уникальные ID ячеек/движений, исходные и итоговые количества, результат проверки/операции. Тексты интерфейса не заменяют эти связи.

Контекст создания проблемы неизменяем: источник (очередь/сборка/Ozon), позиции, количества, текущая подтверждённая ячейка, действующие отборы и их исходные ячейки. Время последнего отбора и время возникновения проблемы — разные события.

Новые события добавляются, старые не перезаписываются. Группировка одинаковых сообщений — только способ отображения. Ошибка внешнего запроса не записывается как успешное решение. Недоступные старые времена сканов не восстанавливаются выдуманными значениями. Архив и просмотр закрытых проблем завершаются на этапе 9.

## Локальная проверка этапа 1

| Сценарий | Обязательный результат |
| --- | --- |
| Остаток положительный, товар физически не найден | Проблема отсутствия в ячейке не решена |
| Собрана 1 из 4, пригодных доступных единиц осталось 3 | Для добора нужно 3; отобранная единица не возвращается в остаток |
| Остаток занят другим заказом | Чужой резерв не используется |
| Заказ вернулся из проблемных | Старый резерв используется/корректируется; второй резерв не создаётся |
| Одна из двух проблем решена | Возврат всё ещё запрещён |
| SKU сопоставлен, товара недостаточно | Проблема SKU решена; нехватка зарегистрирована отдельно |
| Повреждён отобранный товар | Нельзя считать его готовым или автоматически пригодным остатком |
| Количество заказа уменьшено ниже отобранного | Лишние отборы требуют учитываемого физического возврата |
| Отмена без отборов | Освобождение остаточного резерва, отмена и архив, без разбора |
| Отмена с отборами | Только разбор; передача не означает завершение возвратов |
| Повтор подтверждения Ozon успешен | Завершение собранного заказа, без повторного списания |
| Повтор получения данных Ozon успешен | Повторная проверка заказа, без автоматического завершения/возврата |
| Другая проблема подтверждена, известное препятствие осталось | Возврат запрещён |
| Склад изменился после решения нехватки | Повторная проверка при возврате отклоняет недоступный отбор |

Проверка этого этапа — согласованность правил с утверждёнными требованиями и перечисленными сценариями. Интеграционные проверки поведения появятся вместе с реализацией соответствующих этапов; документ не подтверждает работоспособность ещё не написанного backend.
