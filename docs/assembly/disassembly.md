# Передача и физический разбор — этап 8

Источники: утверждённый план, `problem-resolution-rules.md`, `04_DISASSEMBLY.md` и отдельное указание пользователя: **нажатие «Передать в разбор» не возвращает товар в остатки**.

## Передача

Сервер принимает `POST /api/assembly/problems/{problemID}/transfer-disassembly` с прежними `requestId` и `version`. Оператор не передаёт количества, ячейки или движения.

Backend проверяет реальный заказ, необходимость физического разбора, сохранённые действующие отборы и отсутствие параллельной сборки этого заказа. Для отмены требуется сохранённое проверенное подтверждение отмены Ozon. Если результат подтверждения отправления неоднозначен, физический разбор не подменяет выяснение результата этой операции.

Создаются сессия `waiting` и неизменяемый набор единиц, каждая связана с оригинальным pick/товаром/ячейкой. Сохраняются первоначальный контекст и все исходные отборы. Повтор одного запроса возвращает прежний ответ; новое нажатие использует существующую передачу этого заказа. Без реальных отборов сессия не создаётся. Preview-записи не превращаются в реальные возвраты.

Освобождается только оставшийся неотобранный резерв. **Ни передача, ни запуск, ни подтверждение товара не меняют `cell_stock`.** Передача не считается устранением проблемы; состояние заказа — `awaiting_disassembly`.

Обычные действия возврата в сборку, обновления остатков и mapping для переданного заказа блокируются. История и причины остаются в проблемном окне до завершения разбора. Кнопка меняется на «Передан в разбор».

## Окно «Разбор»

Окно находится на странице «Сборка», наследует общий стиль и ширину панелей. Показывает очередь сессий, причины, количество возвращённых/всех единиц, статус и начало/продолжение. Активная область разделена на список товаров с исходными ячейками и панель сканирования, соотношение 3/5 и 2/5.

Показываются прогресс, внутренний SKU и исходный SKU заказа, конкретные ID ячеек/склад, возвращённые количества, последний скан и результат. Источники с одинаковым кодом разделяются по ID. Ошибки скана дают звук и красное свечение viewport через существующий компонент обратной связи.

`Отложить` переводит активную сессию в ожидание, не сбрасывая ни прогресс, ни подтверждённую единицу/ожидаемую ячейку. Можно продолжить другую сессию. Одновременно активен один разбор; сборка другого заказа не останавливается. Фокус восстанавливается только после собственного скана, если оператор остался в форме разбора, а не из-за действий соседнего окна.

## Процесс «товар → исходная ячейка»

Серверные действия: `POST /api/assembly/disassembly/{sessionID}/start`, `/scan`, `/pause`, `/finish`. Используются общий workspace-lock, версия и журнал идемпотентных запросов. Scan дополнительно принимает только `code`.

1. **Товар:** внутренний SKU ищет ещё не возвращённую исходную единицу. Выбор стабилен по порядку первоначальных отборов. Сохраняется конкретный `pending_item_id`; остаток не меняется.
2. **Ячейка:** принимается именно исходный ID этой единицы. Канонический код — `CELL:<ID>`; обычный код допустим только при глобальной уникальности. Неправильная/неоднозначная ячейка не сбрасывает подтверждённый товар и ничего не зачисляет.
3. **Возврат:** одной транзакцией сохраняется уникальное движение возврата, связанное с исходным pick, увеличивается остаток исходной ячейки на 1, сбрасывается pending, обновляются прогресс/лог/история/версия/ответ запроса. Проверяются активная сессия, пригодность товара, архивирование и совместимость категории исходной ячейки. Товар и ячейка блокируются на время операции.

Новая попытка сканировать ячейку после успешного возврата без нового скана товара не создаёт второго зачисления. Уникальность возврата по исходной единице защищает и от другого requestId. Возвращённый pick исключён из действующих отборов, но исходная запись и неизменяемые snapshots не удаляются. Нельзя затем отменить этот pick через прежний undo и зачислить его ещё раз.

При сбое сохранения откатывается всё, включая движение, остаток, pending и историю. После загрузки страницы состояние берётся из БД: сессия, подтверждённая единица, источник и уже выполненные возвраты восстанавливаются.

## Завершение

Завершение доступно после физического возврата всех исходных единиц. Backend повторно проверяет отсутствие pending, незавершённых возвратов, действующих отборов и собственного оставшегося резерва.

Сессия становится `completed`, заказ — `disassembled`. Связанные причины получают терминальный исход `disassembled`, с сохранением прежних данных и истории. Отмена считается обработанной после полного физического возврата; другие причины не объявляются искусственно устранёнными. Закрытые записи исчезают из рабочих списков, оставаясь в БД. Возврат такого заказа в сборку и повторный запуск той же сессии запрещены.

Архив и просмотр закрытых проблем остаются этапом 9.

## Хранение

Миграция `018_assembly_disassembly.sql`: сессии, неизменяемые исходные единицы, неизменяемые реальные возвраты, связи с первоначальными warehouse operations и журналом HTTP-запросов. Отдельные новые таблицы расширяют существующую модель заказов; старые миграции/контекст/отборы не переписываются.

`disassemblySessions` в ответе workspace вычисляется из нормализованных таблиц. Снимок страницы не является источником количеств разбора. Переходы заказа отражаются в прежних `assembly_order_records`. История получает передачу, запуск, паузу, каждый физический возврат и завершение; группировка сообщений не переписывает события.

## Проверки

Локальные PostgreSQL сценарии используют отдельные временные схемы:

- передача/повтор передачи/запуск без зачисления;
- семь единиц из двух ячеек, одинаковые коды и возврат точно по ID источника;
- товар → ячейка, неверный/лишний товар, неверная ячейка с сохранением pending;
- GET/reload, пауза/продолжение с подтверждённой единицей;
- повтор после потерянного ответа, новый запрос с прежней ячейкой, конкурентный одинаковый запрос и устаревшая вкладка;
- сбой после записи движения возврата: полный откат остатка, pending и истории;
- запрет двойного undo уже возвращённого pick;
- повреждённый/архивный товар и изменение категории исходной ячейки;
- запрет передачи без отборов, запрет возврата в сборку и раннего завершения;
- повтор проверенной отмены после частичного физического возврата;
- полный возврат: восстановление исходных остатков, отсутствие резерва, состояние `disassembled`, сохранность первоначальных snapshots и отборов;
- регрессии этапов 1–7.

Пройдены `go test ./...`, `go vet ./...`, профильные повторные проверки после последних исправлений, шесть frontend-скриптов, lint, TypeScript/Vite build, `git diff --check`. Frontend проверяет состояния панели, разделение ячеек по ID, баркод после mapping, завершение/скрытие, идентичность повторов. Проверки GitHub Actions и push не используются.

## Ограничения

- Разбор реализует физический возврат исходных единиц полного заказа в исходные ячейки. Частичная переработка изменённого состава требует своего согласованного workflow; этот этап не делает её произвольным пересчётом.
- Повреждённые единицы сохраняются, но **не зачисляются в пригодный остаток**. Отдельного процесса карантина/утилизации/подтверждения пригодности в проекте пока нет; такой разбор не сможет завершиться обычным возвратом. Можно отложить его без потери состояния. Это предохранитель, а не фиктивное решение повреждения.
- Изменение категории/архивирование блокируют зачисление; произвольная другая ячейка не предлагается как обход.
- Подключение официального Ozon-клиента по-прежнему отложено. Проверенное подтверждение отмены использовано только в изолированных тестах; искусственные отмены/заказы в рабочую БД не добавляются.
- Авторизация конкретного оператора пока не предусмотрена приложением; сохраняются серверные время, requestId и связи операций.
