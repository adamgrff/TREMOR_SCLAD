# Проверки «Разбора» — R4.1.1 / R4.3

Этап меняет только тесты и их фикстуры. Компонент, DS v1.0, API, миграции,
складские операции и бизнес-правила остаются прежними.

## Визуальный эталон

`frontend/scripts/fixtures/disassembly-visual-baseline.json` закрепляет полный
commit SHA `83f84abaa17a1ac45eabdbea00e4d2124d550d57`: вручную принятый
«Разбор» R4.2 с кнопкой отмены возврата. Прежний `bb0bd416` заменён по
прямому согласованию пользователя в R4.3. Это не `HEAD` и не pre-DS-тег.
Коммит должен присутствовать в локальном Git checkout; для shallow clone нужно
предварительно получить этот коммит. Автоматической перезаписи эталона нет.
Смена эталона требует отдельного согласования, проверки diff и просмотра кадров.

`check-design-system-visual.mjs` рендерит отдельно версию этого коммита и рабочую
версию. Каждая использует собственные CSS, импортированные tokens, шрифты и
изображения. Отсутствующий ресурс завершает проверку ошибкой; сеть/API исключены.

Матрица: dark/light × 1920/1000/390 × empty/waiting/paused/product/cell/error/
blocked/complete. Для каждого состояния проверяются обычный кадр, hover и focus
трёх нижних кнопок: отмена возврата, отложить и завершить, включая disabled
и фактическую возможность получения фокуса.
Всего 336 сравнений пикселей, computed styles, геометрии и состояния элементов.
Анимации отключены только в статической визуальной регрессии.

Тестовая временная смена цвета доказывает, что проверка обнаруживает реальные
изменения стилей и пикселей. Она выполняется только в отдельной браузерной
фикстуре и не записывается в приложение/эталон. При несовпадении сохраняются
диагностические кадры/стили вне репозитория, в `TREMOR/checkpoints`.

## Запуск frontend

Из `frontend`:

```powershell
npm test
npm run lint -- src scripts vite.config.ts
npm run build

# Указать существующий установленный Playwright; зависимости проекта не менять.
$env:PLAYWRIGHT_MODULE = 'C:/absolute/path/to/playwright/index.mjs'
node scripts/check-design-system-visual.mjs
node scripts/check-disassembly-feedback.mjs
```

Для браузерных проверок по умолчанию используется локальный Edge. Другой
Chromium можно указать через `BROWSER_EXECUTABLE`. `VISUAL_THEMES=dark` или
`light` ограничивает повторную проверку темой; полный прогон включает обе.
`VISUAL_OUTPUT` и `FEEDBACK_OUTPUT` задают каталоги диагностических артефактов.

`test-disassembly.mjs` проверяет существующие состояния, смешанную очередь,
блокировки действий, оба шага сканирования, суммарный прогресс SKU и отдельные
исходные ячейки с одинаковым кодом, но разными ID. Проверяется неизменность
переданных исходных данных.

`test-scan-error-feedback.mjs` исполняет настоящий хук с управляемым временем
и наблюдателем WebAudio: portal в body, таймер 650 мс, повтор ошибки, истечение,
закрытие audio context и визуальный fallback при недоступном аудио.

`check-disassembly-feedback.mjs` собирает настоящий компонент и настоящий хук
в памяти средствами Vite. Отдельная локальная браузерная фикстура передаёт
отрицательный результат scan через тестовый callback. Проверяются реальный DOM
portal, CSS красного свечения, его исчезновение, неизменный прогресс и отсутствие
feedback при успешном callback. Наблюдаются вызовы настоящего браузерного
AudioContext/oscillator. Слышимость, громкость и качество звука в headless-среде
не подтверждаются. Никакой альтернативной реализации feedback не добавляется.
Для стабильного снимка тест приостанавливает настоящую CSS-анимацию и управляет
браузерными часами: на 649 мс portal ещё существует, на 650 мс удаляется.
Цвета, классы и production-таймер не подменяются.

## Backend / PostgreSQL

Из `backend`, с локальной переменной `TEST_DATABASE_URL`:

```powershell
go test ./cmd/api -run '^TestDisassembly' -count=1 -v
go test ./... -count=1
go vet ./...
```

Существующие интеграционные helpers создают временные схемы с изолированным
`search_path` и удаляют их после теста. Для постоянного CI предпочтительна
выделенная тестовая БД. Значения подключения и ключи не включаются в отчёты.

Четыре независимых finish-blocker сценария: оставшиеся единицы; pending item;
незакрытый исходный отбор; удерживаемый резерв. Для изоляции поздних серверных
guards все единицы предварительно возвращаются обычным handler, затем в
изолированной схеме подготавливается защитная фикстура. В частности, stale
pending после возврата всех единиц — искусственное состояние для проверки
защитного условия, а не новый разрешённый пользовательский процесс.
Триггеры и FK не отключаются.

При отказе сравниваются сессии, остатки, весь реестр возвратов, резервы,
request receipts, workspace и история. Статус остаётся active, успешное
завершение не появляется. Production-логика для тестов не изменяется.

В R4.3 добавлен `TestDisassemblyFinalCycleHTTPUndoReloadAndCompletion`: один
сквозной HTTP-сценарий с настоящими PostgreSQL handlers проходит start, scan,
pause/resume/reload, неверный товар и неверную/неоднозначную ячейку, return,
undo, повторный return, полный возврат, undo, запрет finish и успешное завершение
после повторного return. Каждый успешный/диагностический ответ replay-ится и
сверяется с GET workspace; отдельные ответы намеренно теряются после COMMIT.
Проверяются stale version, исходный контекст, append-only история и восстановление
остатков двух исходных ячеек. Миграция 019 включена и в штатный runner, и в
integration bootstrap, использующий настоящую цепочку складских миграций.
