# Серверная проверка остатков и возврат: этап 4

Правила: [problem-resolution-rules.md](problem-resolution-rules.md). Снимок создания: [problem-creation-context.md](problem-creation-context.md).

## API и согласованность

Кнопки используют POST `/api/assembly/problems/{problemId}/check-stock` и POST `/api/assembly/problems/{problemId}/return`. Тело содержит только `requestId` и ожидаемую `version`; количества и состояние решения клиент не передаёт.

Backend под блокировкой рабочего состояния читает сохранённый состав, действующий снимок отборов, реальные products/cell_stock, резерв и ограничения других проблем заказа. Результат в `assembly_stock_checks`, статус, текущая нехватка, события истории, рабочее состояние и идемпотентный ответ записываются одной транзакцией. События содержат `checkId`, связывающий отображаемый результат с числами и ID ячеек проверки. Ошибка БД откатывает всю операцию.

HTTP 200 означает, что операция обработана и её результат сохранён. `applied=false` означает отрицательный результат проверки/возврата, а не обрыв связи: ответ содержит новое состояние и сообщение. Frontend показывает результат и не зацикливает повтор отрицательного ответа. Повтор при обрыве связи использует прежний requestId; выполненное действие воспроизводится без второй проверки/истории/резерва. Конфликт версии — 409 с загрузкой актуального состояния.

Обычный PUT рабочего состояния не может изменить проблему, историю, состав активного заказа или подделать переход «Решена»/«Возвращена». Начало сборки также проходит серверную проверку и резервирование, хотя кнопка пока передаёт демонстрационный состав через существующий PUT.

## Количества и резерв

- Требуется добрать = количество заказа − сохранённые отборы.
- Доступно = пригодный фактический остаток − резервы других заказов. Собственный оставшийся резерв не вычитается как чужой и не добавляется к физическому остатку повторно.
- `assembly_order_reservations` хранит скрытый оставшийся резерв. При начале сборки создаётся одна запись для каждой пары заказ/товар. При нормальном уходе в проблемные записи сохраняются. Возврат обновляет существующие записи, а не создаёт второй резерв.
- При изменении демонстрационного прогресса резерв соответствует оставшемуся количеству; при завершении он освобождается. Подтверждённые физические отмены и разбор получат свои серверные операции на этапах 7–8.
- Пополнение и отмена приёмки синхронизируются через блокировки строк склада. Серверные резервирования сериализуются блокировками товаров; склад не может уменьшиться между чтением проверяемых строк и фиксацией возврата.

### Временный учёт демонстрационных отборов

Этап 5 ещё не подключён: существующие preview picks не списывают cell_stock. Чтобы уже отсканированная демонстрационная единица не стала доступна другому заказу после уменьшения оставшегося резерва, она учитывается отдельно в `assembly_preview_stock_holds`. Для текущего заказа используется его сохранённое число отборов; для других — их сохранённые временные удержания. Это адаптер черновых отборов, а не дополнительный резерв оставшегося товара и не новое складское движение.

Проверка сохраняет отдельно физический остаток, чужой/свой резерв и временные удержания. Уже отобранное не прибавляется к доступному. Завершение демонстрационного заказа освобождает оставшийся резерв, но удержание его демонстрационных отборов остаётся: реального списания ещё не было. Этап 5 должен заменить такие удержания реальными складскими движениями и исключить двойной учёт. До этого цифры доступности для сборки могут отличаться от физического остатка в каталоге на величину резерва и демонстрационных удержаний.

Миграция не создаёт резервов задним числом для старых снимков, не списывает товар и не меняет реальные остатки. При успешном начале/возврате сервер создаёт согласованный оставшийся резерв по текущим данным.

## Решение и возврат

«Обновить остатки» проверяет весь заказ и обновляет его открытые проблемы недостаточного остатка. Остальные причины не решаются этой кнопкой. Неизвестный/архивный товар, неоднозначные коды ячеек и необходимость физической проверки дают явную ошибку, сохраняют историю и запрещают положительный результат.

Проблемы отсутствия/повреждения товара не позволяют использовать неподтверждённую доступность затронутой позиции до устранения этой причины. Для других типов одного старого статуса `resolved` недостаточно: возврат требует серверного доказательства в `assembly_problem_clearances`, соответствующего типу причины и составу заказа. Эти записи готовят контракт для последующих операций физической проверки, сопоставления и подтверждения данных; сами эти действия здесь не реализованы.

Возврат выполняется только по явной кнопке, при отсутствии другой активной сборки, отмены, незавершённого обязательного разбора, ошибки Ozon и нерешённых проблем. Backend заново проверяет склад непосредственно в транзакции возврата. Если товар больше недоступен, статус недостаточного остатка становится ожидающим, новая нехватка и история сохраняются, заказ остаётся в проблемных. Если такой причины раньше не было, создаётся отдельная проблема с наблюдением `warehouse_check`, не переписывая исходную.

Успешный возврат переносит все открытые проблемы заказа в возвращённые, восстанавливает отборы, сохраняет подтверждение отправления и строит план по текущему доступному количеству. Старое подтверждение ячейки сбрасывается. Несогласованные составы разных снимков или отбор сверх состава блокируют возврат.

## Границы этапа

Реальные заказы Ozon, реальные списания и прогресс, постоянные сопоставления и физический разбор не подключены — это следующие утверждённые этапы. Чтение реального склада для проверки уже работает. При отсутствии соответствующего SKU в products демонстрационный заказ не сможет пройти серверный запуск/возврат: фиктивное наличие из frontend больше не является разрешением.

План сканирования пока использует коды ячеек. Проверка и аудит читают их реальные ID, но при одинаковых кодах и необходимости дальнейшего подбора возврат блокируется; привязка сканирования к уникальным ID относится к этапу 5. SKU пока сопоставляется с products.sku; постоянное сопоставление Ozon SKU относится к этапу 6.

## Обновление и проверки

Мигратор применяет 014 после 011–013. Перед обновлением сохраняются дамп, прежний API и Git-точка `checkpoint-before-server-stock-2026-10-12`. Сам перенос сохраняет текущее состояние и не запускает проверки/резервирование без действия оператора.

Локальные проверки: недостаток/пополнение, повторная нехватка при возврате, собственный/чужой резерв, частичный отбор и повторное использование резерва, несколько причин, серверное доказательство, новая независимая причина, неизвестный/архивный SKU, одинаковые коды ячеек, отказ БД, блокировка складского изменения, идемпотентный повтор и запрет клиентского обхода. Дополнительно Go test/vet, frontend-тесты API-действий/истории, lint/build и сверка рабочего состояния до/после миграции. GitHub Actions не используются.
