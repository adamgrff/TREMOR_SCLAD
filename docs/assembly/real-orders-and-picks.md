# Реальные заказы и отборы — этап 5

## Границы и неизменные правила

Правила [problem-resolution-rules.md](problem-resolution-rules.md), контекст этапа 3 и серверные проверки этапа 4 сохраняются. Этап 5 добавляет адаптер реальных данных к тем же `assembly_order_records`, версиям/позициям, проблемам, отбору, истории и резервам. Отдельного доменного хранилища заказов Ozon нет.

Резерв появляется при начале сборки. При отборе одной единицы `cell_stock` уменьшается на 1 и оставшийся резерв уменьшается на 1 в той же транзакции. Действующие отборы учитываются отдельно от склада и оставшегося резерва. Для реальных заказов preview holds не создаются; уже списанные единицы не вычитаются второй раз при проверке. Исторические preview holds других заказов учитываются прежним адаптером, без автоматического списания/освобождения.

Нормальный уход в проблемы сохраняет оставшийся резерв и действующие складские отборы. Возврат использует существующие проверки всех причин и актуальных остатков, восстанавливает действующие отборы и сбрасывает подтверждение ячейки. Решение одной причины не решает остальные. Правила отмен, сопоставления, подтверждения Ozon и разбора не изменяются; их действия подключаются на последующих этапах.

## Заказы из БД

`GET /api/assembly/orders` читает опубликованные версии заказов с `source=ozon` и `status=queued` из существующей модели. `assembly_order_heads` хранит только указатель на опубликованную версию. `assembly_order_imports` — неизменяемый журнал загрузки. Наблюдения актуального склада для очереди не резервируют товар и не публикуют новые версии.

В frontend удалена демонстрационная очередь. Время/дата берутся из сохранённого `createdAt`, а наличие и план ячеек — с сервера. Начало сборки принимает только номер отправления, без состава и клиентских количеств. Создание проблемы из очереди также получает состав исключительно из БД.

Локальный доверенный импортёр:

```powershell
# Из backend, с локальным DATABASE_URL. Файл содержит настоящие нормализованные данные.
go run ./cmd/import-assembly-orders -file <absolute-path-to-orders.json>
```

Формат файла — массив объектов `{requestId, order}`. `requestId` — UUID. Поля order: `source: "ozon"`, `number` (номер отправления для подтверждения этикетки), `createdAt` (RFC3339), `items`. Позиция: `name`, `sku` (текущий внутренний/согласованный артикул), `quantity`, необязательный `ozonSku` (внешний ID без подмены внутреннего артикула). Поля складских остатков в импортируемом файле не считаются достоверными и обнуляются: их читает складской сервер. Один импорт атомарен; файл с несколькими заказами обрабатывается последовательно, успешно загруженные заказы сохраняются при ошибке следующего. Повтор того же requestId воспроизводит загрузку; другой состав с тем же ID отклоняется.

Возможно обновить состав только ещё не начатого заказа. Уже обрабатываемый, проблемный или завершённый заказ импортёр не перезаписывает и не открывает заново. Изменение такого состава должно пройти утверждённый отдельный процесс согласования версии/резерва/лишних отборов; простой импорт не обходит его. Никаких новых тестовых заказов в рабочую БД миграция не добавляет. Если настоящих опубликованных заказов ещё нет, очередь пуста.

Постоянное сопоставление Ozon SKU относится к этапу 6. Здесь сохраняется согласованный способ этапа 4: поиск `products.sku`; неизвестный/архивный товар не допускает начало сборки. Внешний клиент обязан передать нормализованную позицию, не выдавая числовой Ozon SKU за найденный складской товар.

## Складские действия

POST `/api/assembly/start`, `/scan`, `/undo`, `/finish` используют общий контракт `requestId` + `version` и существующую транзакцию рабочего состояния/журнал повторов. Дополнительно start принимает `orderNumber`, scan — `code`. Клиент не присылает новый прогресс, ID операции, количества или подтверждённый статус. После подключения 015 произвольный PUT снимка не выполняет складских действий.

Сканирование проверяет серверный план и актуальный склад. Подтверждение ячейки позволяет брать любой нужный товар этой ячейки в любом порядке. Когда нужное из ячейки собрано, подтверждение сбрасывается; после всех товаров требуется скан отправления. Неверный скан сохраняет ошибку и не меняет отборы, резерв или склад. При ошибке БД вся операция откатывается.

`assembly_warehouse_operations` хранит неизменяемые движения pick/undo_pick с ID заказа, позиции, товара и исходной ячейки, точным временем и requestId. `assembly_pick_records.source=warehouse_operation` ссылается на это движение. Отмена восстанавливает 1 единицу именно в исходной ячейке и оставшемся резерве, ссылается на отменяемое движение и убирает только последний действующий отбор из прогресса. Исходное движение и его отмена сохраняются. Сканы ячейки и отправления складскими отборами не являются. Отмена после подтверждения этикетки сбрасывает подтверждение отправления, потому что заказ снова не полностью собран.

Остаток, резерв, операция, прогресс, версия рабочего состояния и идемпотентный ответ фиксируются вместе. Повтор после обрыва связи не списывает/возвращает второй раз. Конфликт второй вкладки требует загрузки актуального состояния. Перезагрузка восстанавливает точное подтверждение ячейки, прогресс, подтверждение этикетки и последний скан.

Контекст новой проблемы включает ID операций/отборов/ячеек и точное время. История перед созданием показывает реальные отборы и их отмены; это не выдуманные времена старых preview-сканов. Неизменяемые снимки старых проблем не переписываются.

## Идентичность ячеек

План передаётся структурированно: `cellId`, отображаемый `cell`, склад, `scanCode`, требуемое/собранное/доступное количество. Источники не группируются по одному текстовому коду. Приоритет — минимальный положительный пригодный остаток, затем код, затем ID для стабильности.

Канонический скан — `CELL:<ID>`. Старый текстовый код принимается только если он уникален во всей таблице cells и соответствует ожидаемой ячейке. При одинаковых A1 нужен канонический код; сервер не выбирает случайный стеллаж. UI показывает ожидаемый код и ID, а источники отборов в проблемах различает по ID. Физические старые этикетки неоднозначных ячеек потребуется заменить/дополнить кодом ID, либо отдельно согласовать их существующий уникальный формат.

## Ozon без предположений о контракте

По уточнённому заданию живые FBS-вызовы отсутствуют до официальной OpenAPI. `internal/assemblyorders.OzonClient` задаёт транспортную границу `FetchAssemblyOrders(ctx) -> []Order`; будущий проверенный клиент нормализует ответ и использует тот же `ImportToDB`. Замена транспортной реализации не требует другой модели заказов/проблем/резервов/отборов.

Необязательные `OZON_CLIENT_ID` и `OZON_API_KEY` читаются только backend из окружения/локального .env. В Git добавлен только .env.example с пустыми значениями; .env уже игнорируется. Значения не передаются frontend, не логируются и не входят в данные заказов. Без ключей backend запускается. Даже наличие ключей не означает проверенного подключения: GET `/api/ozon/status` отвечает `disconnected` до подключения настоящего клиента; шапка показывает «Ozon не подключён». Фиктивной успешной синхронизации нет.

`finish` проверяет полный отбор и скан этикетки, но без настоящего подтверждения Ozon возвращает `applied=false` с объяснением. Заказ остаётся активным с сохранённым прогрессом и не получает фиктивный статус завершённого. Скан коробки не подменяет подтверждение внешней операции. На этапе 7 будет подключено фактическое подтверждение/обработка ошибок и повторов; переход завершения использует существующую модель заказа. Отдельные реальные возвраты через окно «Разбор» — к этапу 8.

## Проверки и перенос

Миграция 015 не удаляет старые заказы, проблемы, контекст или отборы и не меняет остатки. Демонстрационные записи остаются историческими, явно помечены в UI и не запускают реальные списания/возврат в сборку. Автоматически превратить старые фиктивные сканы в складские операции нельзя: реальное физическое действие по ним не подтверждено.

Перед применением — Git checkpoint, дамп БД, копия API и снимок рабочего состояния. Локальные PostgreSQL-проверки выполняются в отдельных удаляемых схемах, не на складских данных: полный цикл start/cell/pick/undo/problem/check/return/shipment/finish; произвольный порядок товаров одной ячейки; повторная отмена/подтверждение; одинаковые коды; свои/чужие резервы без двойного учёта; неизвестный SKU; обновление очереди и запрет переписать начатый заказ; сбой после обновления остатков; параллельные повторы и устаревшая вкладка; запрет подделки прогресса; восстановление после GET.

Дополнительно: регрессии предыдущих этапов, frontend API-тесты повторов, SSR-проверки ID ячеек/прогресса, lint, tsc/Vite, go test/vet, отсутствие ключей в Git и проверка сохранности рабочего снимка/склада после миграции. GitHub Actions и push не используются. Финальная комплексная проверка всей цепочки остаётся этапом 10.

После локального применения 015: API/страница отвечают 200, рабочий снимок совпал с сохранённым до миграции, контрольная сумма всех пар ячейка/товар/количество совпала. Новых складских операций и импортов в рабочей БД — 0; настоящих заказов source=ozon пока нет, поэтому очередь пуста. Проверки реальных операций выполнялись на тестовых данных в изолированных схемах, а не посредством списания товаров рабочего склада. Повторный запуск мигратора безопасно пропускает применённые миграции.
