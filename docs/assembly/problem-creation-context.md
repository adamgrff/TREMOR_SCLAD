# Создание проблемы: этап 3

Правила: [problem-resolution-rules.md](problem-resolution-rules.md). Хранение этапа 2: [problem-storage.md](problem-storage.md).

## Создание

Оба окна вызывают POST `/api/assembly/problems`:

```json
{
  "requestId": "UUID",
  "version": 26,
  "source": "queue",
  "orderNumber": "024833-0001",
  "order": { "number": "024833-0001", "items": [] },
  "details": {
    "type": "insufficient_stock",
    "positionSku": "TR-WHITE",
    "comment": ""
  }
}
```

Пример показывает контракт; массив items в настоящем запросе должен содержать корректные позиции с количеством и снимком доступности. Для `source=assembly` поле order не отправляется: заказ и весь прогресс берутся из сохранённого серверного состояния. Клиент не передаёт отборы, подтверждённую ячейку или самостоятельно составленную историю.

Для причин «Недостаточно товара», «Товар отсутствует в ячейке», «Неизвестный товар / SKU», «Повреждённый товар» обязательна позиция из заказа. Для ошибки данных и другой проблемы можно выбрать позицию либо заказ целиком. Для другой проблемы обязателен непустой комментарий.

В одной транзакции под блокировкой версии сервер проверяет источник/состав/прогресс, создаёт проблему и события истории, сохраняет контекст и переносит активный заказ в проблемные. Ошибка не очищает активную сборку. Повтор одного requestId воспроизводит результат без второй проблемы; повтор того же ID с другим содержимым и устаревшая версия отклоняются. Общий PUT рабочего состояния больше не создаёт проблемы в обход этого действия.

## Сохранённый контекст

`assembly_problem_contexts` содержит неизменяемый снимок; он возвращается через API как `problem.creationContext`:

- источник `queue` / `assembly`, серверное время создания;
- ID заказа, исходной версии состава и каждой позиции;
- все позиции и отдельный непустой список затронутых позиций;
- по каждой позиции: требуется всего, отобрано, осталось добрать, доступно по снимку, не хватает, исходные данные ячеек;
- общий прогресс, состояние сканирования `cell` / `product` / `shipment`;
- подтверждённая и следующая предлагаемая ячейки; их самостоятельные ссылки;
- полный сохранённый activeState, включая последний скан, сообщение и признак ошибки;
- исходные отборы: SKU, ячейка, ID записи отбора, ссылка на ячейку, ссылки на реальные операции и время, если они известны;
- подтверждение отправления, исходная причина и комментарий в записи проблемы этапа 2.

Все обнаруженные в снимке нехватки сохраняются, а не только первая. Выбранная позиция сохраняется и при отсутствии нехватки. Для проблемы без выбранного товара затронутым считается весь состав заказа. UI использует сохранённые позиции и показывает их количества даже для причин, у которых список нехватки пуст.

Подтверждённые отборы не складываются с доступностью. В черновой сборке исходный план ячеек содержит демонстрационные отборы; из его количества они вычитаются один раз. После обновления плана скалярный stock уже может исключать отборы, поэтому повторно вычитать их из этого числа нельзя. Эта совместимость чернового плана не заменяет серверную складскую проверку.

## Миграция и границы

Мигратор применяет 013 после 011–012. Существующие проблемы сохраняют свои ID, статус, историю, состав и отборы. Для них добавляется контекст из известных исходных записей с `complete=false`; неизвестное состояние сканирования и время старых сканов не придумываются. Для новых проблем `complete=true` означает полный контекст текущей демонстрационной модели.

Из очереди пока передаётся демонстрационный состав заказа, поскольку реальная очередь ещё не подключена. Доступность фиксируется по сохранённому снимку с `availabilitySource=preview_snapshot`; обращения к реальным остаткам/резервам и разрешение решения относятся к этапу 4. Реальные заказы, отборы, операции и ID складских ячеек относятся к этапу 5. Физическое отсутствие или повреждение не доказывается числом из снимка: проверка оператора и складская обработка остаются следующими этапами.

Таблица контекста не меняет остатки, резервы или складские операции. UPDATE/DELETE снимка запрещены. При последующей проверке проблемы меняются текущие сведения, а исходный контекст остаётся прежним.

Перед локальным обновлением: дамп БД, копия прежнего API, Git-точка `checkpoint-before-problem-context-2026-10-11`. Затем остановка прежнего API, `go run ./cmd/migrate-assembly-preview` из backend и запуск нового API. Полный дамп нельзя восстанавливать поверх последующих действий без отдельного согласования; первичный снимок не заменяет актуальные данные.

## Локальные проверки

- PostgreSQL в изолированных схемах: очередь, несколько нехваток, частичный отбор, идентичность отборов/ячеек, перезагрузка, повтор/конфликт запроса, отклонение неполного контекста, неизменность снимка и перенос старых записей.
- Go: все три состояния сканирования, подтверждённое отправление, сообщения и расчёт после восстановления плана; `go test ./...` и `go vet ./...`.
- Frontend: выбор позиции в очереди, обязательный комментарий, защита от повторного действия, тот же запрос при обрыве связи, загрузка состояния при конфликте; действующие проверки остатков/истории, lint и build.
- GitHub Actions не запускаются; push не выполняется.
