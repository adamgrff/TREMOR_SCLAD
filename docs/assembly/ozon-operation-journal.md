# Журнал Ozon и безопасные повторы — этап 7

## Согласованная граница этапа

По уточнению пользователя реализована **безопасная внутренняя основа без FBS-вызовов**. Официальная спецификация не получена. Существующий `internal/assemblyorders.OzonClient` не изменён; интерфейс адаптера, транспортные методы и их реальные контракты отложены до отдельного согласованного подключения по официальной спецификации. Сторонние Swagger и предполагаемые endpoint не используются.

Правила этапов 1–4, нормализованные заказы/проблемы/отборы и скрытый резерв сохранены. Изменение разрешения возврата уточняет предусмотренный правилами случай: проверенное получение данных может разрешить **явный** возврат, подтверждение собранного отправления — завершение, отмена — свой путь. Эти исходы не взаимозаменяемы.

## Исходная операция и попытка сверки

Миграция `017_assembly_ozon_operations.sql` добавляет:

- `assembly_ozon_operations`: неизменяемые ID операции, ID заказа/версии, назначение `confirm_shipment` / `refresh_order`, постоянный `business_key`, SHA-256 смыслового содержимого и сохранённый контекст.
- `assembly_ozon_problem_links`: неизменяемую связь проблемы с исходной операцией; другая операция/другой заказ вместо исходных запрещены.
- `assembly_ozon_reconciliations`: попытки сверки, связанные с исходной операцией и существующим журналом HTTP-запросов. В текущем режиме фиксируется недоступность официального клиента.
- `assembly_ozon_observations`: неизменяемые внутренние записи проверенных результатов с уникальной идентичностью свидетельства, временем проверки и связью с точным отпечатком операции.

`requestId` нажатия и постоянный ключ бизнес-операции — разные идентичности. Новый HTTP-запрос сверки не создаёт новую бизнес-операцию. Повтор того же HTTP-запроса возвращает ранее сохранённый ответ. Нельзя заменять содержимое существующего запроса/свидетельства или создать изменённую операцию вместо операции с неизвестным/подтверждённым результатом.

**В этой реализации вообще нет пути отправки бизнес-операции в Ozon.** Даже внутренний результат `not_applied` не запускает отправку. Это не обещание внешней exactly-once гарантии: её возможности можно установить только по официальному контракту. При будущем подключении необходима проверка фактического состояния исходной операции перед рассмотрением отправки, особенно после таймаута, падения процесса или потерянного ответа. Наличие локального UUID не доказывает идемпотентность внешнего сервиса.

## Поведение интерфейса сейчас

После полного отбора и скана отправления `Завершить сборку` сохраняет исходную операцию подтверждения. Без официального клиента заказ не завершается фиктивно, а попадает в проблемные с полным прогрессом и указанием, что подтверждение ожидает сверки. Складские движения при этом не выполняются заново.

`Повторить запрос Ozon` отправляет только локальное действие `POST /api/assembly/problems/{problemID}/retry-ozon` с `requestId` и `version`. ID исходной операции берётся сервером из проблемы. Клиент не присылает бизнес-ключ, результат или новый состав. В текущем режиме ответ явно сообщает: фактическая сверка недоступна, операция сохранена, повторная отправка запрещена. Недоступность клиента не записывается как якобы выполненная проверка Ozon.

Старые проблемы без исходной серверной операции не получают новую операцию кнопкой повтора. Исторические preview-заказы также не выполняют реальные действия.

## Обработка проверенного внутреннего результата

`ingestOzonDomainReceipt` — внутренний обработчик будущего доверенного источника. **Публичного HTTP endpoint для передачи результата нет.** Это не интерфейс Ozon-адаптера и не схема ответа Ozon. Термины `unknown`, `not_applied`, `applied`, `rejected`, `cancelled` обозначают внутренние выводы после проверки источником, а не предполагаемые wire-статусы внешнего API.

Доверенный источник ещё предстоит реализовать по официальной спецификации; он обязан доказать результат для исходных заказа/операции/содержимого. HTTP 200, произвольный текст или клиентский флаг не являются таким доказательством. В текущем рабочем приложении этот обработчик не получает сетевых данных и не используется для симуляции успеха.

Сейчас обработчик проверяет идентичность операции/заказа/отпечатка, время, повтор свидетельства и согласованность перехода. Сырые wire-ответы и секреты не сохраняются; входная версия заказа приводится к уже существующей модели `assemblyorders.Order`. Устаревший результат не заменяет новый; проверенный успех не заменяется неизвестностью/отказом, отмена не снимается этим путём.

Свидетельство, состояние проблем/заказа, локальные проверки и история фиксируются в одной транзакции. При ошибке публикации всё откатывается; повтор применения того же свидетельства безопасен. Внешних запросов внутри транзакции нет.

### Подтверждение собранного отправления

После проверенного успеха устраняется только связанная ошибка Ozon. Завершение дополнительно требует полного действующего отбора, подтверждённой коробки, согласованного состава, нулевого оставшегося резерва и отсутствия других препятствий. Для других причин проверяются серверные доказательства этапов 1–4, а не только строка «Решена». Заказ завершается один раз, без новых отборов и списаний. При другом препятствии он остаётся проблемным.

Если другие причины устранены позже, для дальнейшего применения нужен новый проверенный результат доверенного источника. Текущая кнопка сверки не подменяет это свежим якобы полученным ответом.

### Получение / проверка данных заказа

Успех чтения требует полноценной проверенной версии заказа. При неизменном составе backend проверяет текущий склад, создаёт отдельную нехватку/неизвестный SKU при необходимости и сохраняет доказательство проверки заказа. Другие причины остаются независимыми. Само чтение не запускает и не завершает сборку.

`Вернуть в сборку` разрешается только после общего решения причин и проверенного результата именно операции чтения. Существующая операция возврата повторно проверяет актуальные остатки/резерв и серверные доказательства.

Если состав изменился, создаётся отдельная проблема данных; прежние состав, отборы и резерв не переписываются. Повторное чтение с тем же сохраняющимся препятствием не плодит одинаковые причины. Применение изменённого состава и обработка лишних отборов требуют своего согласованного workflow; они не реализованы произвольным присваиванием в данном этапе.

### Отмена заказа

Проверенная отмена создаёт самостоятельную проблему отмены и останавливает активную сборку этого заказа. Действующие отборы с исходными ячейками сохраняются. Освобождается только оставшийся неотобранный резерв; `cell_stock` не меняется.

Без отборов доступно явное `Закрыть отменённый заказ` — `POST /api/assembly/problems/{problemID}/close-cancelled`. Сервер проверяет доказанную отмену, отсутствие реальных действующих отборов, оставшегося резерва и обязательного разбора. Заказ становится `cancelled`, а связанные причины получают отдельный терминальный исход с сохранением истории. Это не возврат в сборку и не утверждение, что каждая прежняя причина была устранена.

При отборах закрытие запрещено, требуется физический разбор. Его выполнение остаётся этапом 8; автоматического возвращения товара в ячейки нет. Отмена уже локально завершённого заказа намеренно отклоняется как требующая отдельной обработки, а не откатывает завершение/склад автоматически.

Закрытые записи сохраняются в БД и исключаются из рабочего списка. Архив и просмотр закрытых проблем остаются этапом 9.

## Локальные проверки

В отдельных временных PostgreSQL схемах проверены:

- повтор HTTP после потерянного ответа и повторные нажатия с новыми ID — одна исходная операция;
- неизвестность, неподтверждённое выполнение и отказ — без решения/завершения/новой отправки;
- позднее подтверждение ранее выполненной операции — одно локальное завершение, без повторного склада;
- повтор и параллельное применение свидетельства, конфликт его содержимого, неверный заказ/отпечаток, устаревший результат;
- запрет замены исходного ключа/неизвестной операции;
- полный откат результата/состояния/истории при ошибке публикации;
- отмена без отборов и с частичным отбором, освобождение только собственного оставшегося резерва;
- проверенное чтение без автоматического старта, новая нехватка/ошибка состава;
- возврат после чтения с повторной проверкой изменившегося остатка;
- подтверждение отправления при другой причине и запрет обхода серверного доказательства меткой «Решена»;
- регрессии этапов 1–6.

Frontend: одинаковое тело и `requestId` при повторе, назначение кнопок по типу операции, блокировка возврата другими причинами, скрытие терминальных исходов, запрет закрытия отмены с отборами. Локально выполнены `go test ./...`, `go vet ./...`, пять frontend-скриптов, lint, TypeScript/Vite build и `git diff --check`. GitHub Actions и push не используются.
