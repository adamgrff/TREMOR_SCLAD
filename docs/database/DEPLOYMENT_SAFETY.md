# Deployment Identity и безопасность восстановления

Статус DB-03.6: документация для ревью. Основной путь — **новая пустая clean-v2**, не upgrade существующего склада. См. [runbook](CLEAN_DEPLOYMENT.md), [checklist](DEPLOYMENT_CHECKLIST.md), [release review](DB03_RELEASE_REVIEW.md).

## Постоянная identity

Миграция `backend/migrations/024_deployment_identity.sql` создаёт одну запись `public.deployment_identity`. Случайный UUID создаётся PostgreSQL один раз при provisioning; имя БД, IP, порт и warehouse ID не используются для его вычисления. Рестарт API и повтор миграций не меняют UUID. Ограничения singleton/unique/not-null и защитные UPDATE/DELETE/TRUNCATE-триггеры проверяются validator.

UUID публичен и не является секретом, авторизацией или правом доступа. Владелец/суперпользователь может обойти DDL-защиту; роли и права требуют DB-04. `/health` подтверждает только доступность процесса: он не доказывает правильную БД. Проверять отдельно SQL target, ledger, UUID и фактические подключения API.

`GET /api/deployment` — read-only, `Cache-Control: no-store, max-age=0`, `Pragma: no-cache`. API не создаёт отсутствующую identity при чтении и не ремонтирует старую схему.

## Серверный барьер каждой команды

Изменяющие запросы передают `X-Tremor-Deployment-Id`. Сервер сравнивает его с фактической строкой PostgreSQL **внутри транзакции**, `FOR SHARE`, до складских эффектов и поиска успешной квитанции. Даже совпавший UUID запроса в другой БД не позволяет прочитать чужую квитанцию.

Защищены создание сессии, сканирование, удаление pending SKU, POST/PUT ручного количества, размещение, undo, завершение, удаление истории, POST/PUT каталога (включая архивирование). Основная реализация: `backend/cmd/api/deployment_identity.go`, `receiving_operations.go`, `receiving_sessions.go`, `receiving_quantities.go`, `receiving_history.go`, `product_catalog.go`.

| Ответ | Значение | Действие оператора |
|---|---|---|
| 400 `deployment_identity_required` | Заголовок отсутствует/некорректен | STOP; проверить согласованность версий frontend/API и контекст |
| 409 `deployment_identity_mismatch` | Другой deployment | STOP; сохранить команду; не считать бизнес-отказом |
| 503 `deployment_identity_unavailable` | Identity нельзя подтвердить | Только просмотр; восстановить доступность/схему, не генерировать UUID |

Identity-ошибки не содержат `X-Receiving-Command-Rejected: true`. Они не доказывают отмену предыдущей доставки. Сетевая ошибка, timeout и 5xx тоже не доказывают rollback.

## Источник UI-данных — часть команды

Snapshot сессии, страницы истории и каталога возвращает deploymentId вместе с данными из согласованной read-only транзакции. История/каталог не получают новую identity автоматически для старых ID. `sendReceivingAction(action, expectedDeploymentId, synchronize)` сравнивает identity исходного UI с текущим API **до создания новой команды**. При несовпадении не создаётся UUID/journal-entry и не отправляется изменение.

Диалог количества получает identity исходной сессии/каталога; lookup SKU тоже должен принадлежать ей. Page проверяет snapshot своим экземпляром journal: другая форма, подтвердившая B глобально, не может перепривязать страницу A. Явная загрузка нового каталога сбрасывает старые editor/draft/dialog; обновление истории закрывает её pending-delete dialog.

Отсутствие активной приёмки само по себе не запрещает чистое редактирование каталога. Запрет по identity/journal — отдельный барьер; создание/редактирование кодов без количества разрешено в нормальном подтверждённом контуре.

## Браузерный журнал

`frontend/src/pages/ReceivingPage/receivingScanCommands.ts` хранит неизменные requestId, payload и deploymentId до отправки. Ключ команды: `tremor.receiving.scan.<UUID>`; новая привязанная сессия: `tremor.receiving.activeSession.v2`. Старый `tremor.receiving.activeSessionId` не используется для автоматической привязки и остаётся сохранённым.

- Одна доказанно привязанная команда восстанавливается прежним UUID против исходного deployment; после подтверждения результата читается актуальное состояние.
- Несколько незавершённых команд с неизвестным порядком: ручное разрешение, автоматического replay нет. Порядок localStorage/Map не считается порядком операций.
- Legacy без identity, foreign command/activeSession, повреждённый journal: не привязывать к текущей БД, не переписывать payload/UUID, не удалять. STOP для записей.
- Отказ localStorage или identity endpoint: запись запрещена, по возможности доступен просмотр серверных данных.
- Неопределённый чистый catalog write без поступления не имеет серверной квитанции в существующей модели; автоматического replay нет, требуется ручная проверка. Не повторять PUT вслепую: он может затереть позднее изменение.

Не выполнять автоматическую очистку localStorage, массовое удаление storage-ключей или замену UUID «для разблокировки».

## Смена API или БД

Предпочтителен отдельный browser origin **и** отдельный профиль для независимого контура. Origin определяется scheme/host/port; другой URL path или query не изолирует storage. Два разных API URL при прежнем frontend origin разделяют один storage — смена API не делает старые команды безопасными.

При плановой смене deployment: остановить новые действия, выяснить все незавершённые команды в исходной БД, сохранить доказательства, согласовать новый контур, затем явно загрузить его данные в отдельном origin/profile. Нельзя просто заменить DATABASE_URL под живым API и предложить пользователям продолжить старые формы. Серверный барьер остаётся необходим даже после успешного handshake: БД может измениться между handshake и POST.

При mismatch не многократно нажимать старую форму. После выяснения pending/identity безопасно обновить страницу/каталог/историю и убедиться, что показаны данные нового deployment. Если остались foreign records, блокировка намеренная — повторная загрузка не должна удалять их автоматически.

## Ручное разрешение зависшей команды

1. Прекратить новые складские изменения; сохранить исходный JSON, requestId, deploymentId, вид операции, время и ошибку в защищённый инцидентный пакет. Не публиковать реальные бизнес-данные в общие логи.
2. Администратор независимо подтверждает target/cluster/deployment и доступность исходной БД. Legacy без доказанной identity нельзя автоматически приписать текущему складу.
3. Прочитать квитанции и фактические операции в исходной БД. Receipt tables: `receiving_quantity_requests`, `receiving_operation_requests`. Проверять UUID, тип и канонический payload, а не только совпадение SKU/количества.
4. Если поддерживается безопасный replay и это тот же deployment — повторить **исходную команду** штатным механизмом восстановления. Потеря ответа после COMMIT должна вернуть квитанцию без нового эффекта. Не создавать новый UUID для выяснения старого результата.
5. Если доказательств недостаточно, несколько команд имеют неизвестный порядок либо это неопределённый catalog-only write — оставить блокировку, передать владельцу/разработчику на согласование. Публичного UI/tool автоматического разрешения сейчас нет.
6. Любое ручное изменение пользовательского journal — отдельная согласованная процедура с сохранением оригинала, решением по каждой команде и проверкой склада. Этот документ не разрешает очистку данных и не содержит команды её выполнения.

## Неопределённый COMMIT provisioning

Migration runner атомарно фиксирует SQL и ledger-row, использует session advisory lock. После ошибки COMMIT не выполняет SQL слепо: переподключается read-only, сверяет тот же server identity/database OID и журнал. `commit_resolved=true`/ошибка о продолжении означает подтвердившийся commit и необходимость повторного `apply` с тем же target/manifest. Неустановленный исход — STOP, затем проверка `status` и тот же `apply` под блокировкой после подтверждения target. Отсутствие строки сразу после сетевого сбоя ещё не доказательство rollback.

После неопределённого warehouse bootstrap повторяют тот же bootstrap с **точно тем же названием**: один склад/no-op или конфликт. Не запускать прямой INSERT. После начала бизнес-заполнения этот initial bootstrap уже не применяется.

## Backup/restore и клоны

Восстановление **того же логического склада** сохраняет identity, ledger, квитанции и историю согласованно. Перенос host/port/database name не означает новый deployment. Старый backup может потерять подтверждения операций после его recovery point: перед авто-восстановлением браузерных команд требуется сверка этих операций. UUID сам не восстанавливает утраченную историю.

**Независимый клон** должен получить другую identity по явно согласованной offline-процедуре. Безопасный реализованный путь — новая пустая clean-v2. Для клона с данными готового rekey CLI/утверждённой процедуры нет: необходимы отдельное доказательство target, backup, остановка writers, защита исходного склада, сохранение receipts, согласование назначения нового UUID и проверка guards. Нельзя автоматически ротировать UUID в startup/GET или отключать защитные триггеры по этому документу.

Автоматическая ротация сломала бы принадлежность уже записанных команд и скрыла бы ошибку подключения. Совпадающая identity у восстановленного независимого клона, напротив, позволила бы старым клиентам считать его исходным складом. Поэтому различие «тот же склад / независимый клон» решает владелец до запуска клиентов.

## Профили и upgrade

| Профиль | Цепочка | Назначение |
|---|---|---|
| clean-v1 | 21 schema-миграция до 023; без identity | Прежний исторический clean-профиль |
| clean-v2 | Те же 21 + 024, всего 22 | Утверждённый новый clean-install |

Оба исключают demo 002 и отмечают 006 историческим gap. Manifest v1 не переписан. Ledger marker/profile v2 отличаются; CLI default manifest всё ещё v1. `v2` поверх существующего v1 отвергается даже при пустых бизнес-таблицах. Ручное применение 024 не превращает v1 в корректный v2 ledger.

**Нет утверждённого безопасного upgrade существующей рабочей БД.** Требуется отдельный проект переноса/обновления с сохранением исходных ledger-row, квитанций, складских событий и согласованием пользовательских pending-команд. Нельзя массово менять profile/checksum/marker либо переименовывать старую БД ради обхода target-защиты.
